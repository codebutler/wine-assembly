Why this is not a one-guard change

win16_guest_request_begin is a singleton PE stdcall request, rejects an existing
pending request, captures a 32-bit linear ESP/return and settles by adding 8/12
bytes. The outer PE LoadLibrary16 request is still pending during this LibEntry.
A nested Win16 call instead has SS:SP, a far return and Pascal four-byte name
argument. Neither overwriting the singleton nor calling its settle export is
valid. invokeNeEntrySync and invokeNeQtSync reject every yield; createNeLifecycle
has no scoped source-service context to pass to a recursively invoked guest.
Module claim rejects initializing/unloading identities and exposes only ready
images. Source closure skips fixed builtins only as dependencies: directly
loading WIN87EM through prepareNeSources still requests a file. Existing fixed
builtin import identities have no owned explicit LoadLibrary reference record.
The native frame chain already supports same-owner nesting, CPU restoration,
module call pins, execution leases and sync-depth cache pins; reuse those
invariants rather than introducing a second loader.

Implementation stages (production remains fail-fast until all enabled paths pass)

1. Add a separate frame-owned nested request record, never the PE singleton.
   Bind it to full frame generation token, owner/thread, process lifetime,
   request serial and captured SS:SP/CS:IP. Accept only a live running frame
   with no unresolved request in that frame. Decode and validate the complete
   far-return/argument span and bounded far string before mutation. Park dispatch
   without changing the far return. Expose only exact-token read/settle/cancel.
   Settlement after child teardown validates the same frame and stack, writes
   AX and performs the existing Win16 Pascal far-return mechanics for four
   argument bytes. Preserve high register halves, DS/ES/SS, flags and parent
   request. Cancellation invalidates before frame storage can be reused.
   Do not allocate frame fields by copying addresses: use declared layout and
   audit the current frame scratch bound and all snapshot/restore consumers.

2. Pass an internal synchronous lifecycle context down serviceNeGuestYieldSync,
   createNeLifecycle and both invocation drivers. It carries the exact facade,
   memory, synchronous VFS resolver, cancellation and one shared remaining-work
   budget plus maximum nesting depth. A nested yield dispatches only this owned
   service; unrelated yields still fail loudly. Child frames acquire the same
   owner execution lease and sync-depth pin while the suspended caller retains
   its own module pin. No await, scheduler borrowing or DLL mutex across guest
   execution/source service. Count all child blocks against the outer budget;
   resetting a fresh 100000-block allowance per recursion is not bounded work.
   Promise-returning source resolvers remain explicitly unsupported.

3. Implement explicit LoadLibrary ownership for fixed fileless builtins as well
   as real image/dynamic modules. WIN87EM must resolve the actual fixed dispatcher
   identity, with no synthetic DLL or fake initializer. Keep permanent dispatcher
   availability separate from acquired guest references; use stable module handle
   aliases and real usage accounting. Define matching FreeLibrary/GetModuleUsage
   behavior and ensure GetProcAddress resolves that same identity. Fixed module
   handles must not be mistaken for owned image records or DGROUP selectors.
   CARDS still requires its real image and must not enter this fileless path.

4. For real DLLs, resolve/copy the closure synchronously and use the existing
   native claim/link/stage/LibEntry/publish transaction. A ready duplicate adds
   one explicit reference; a fresh load becomes visible only after successful
   LibEntry. A nested load is an explicit acquired reference, not an automatic
   bitmask import dependency: repeated loads need repeated releases. Journal
   each acquired reference until settlement; if settlement fails, release the
   unreturned acquisition. After successful settlement the guest owns it, even
   if its caller later rejects initialization; do not silently invent unloads
   for already-returned handles. Import dependencies still roll back with their
   failed transaction. WEP failure retains the actual termination record and
   recovery ownership; aggregate cleanup failures without hiding the cause.

5. Recursive loads of an initializing ancestor must stay a precise diagnostic
   until an explicit same-owner provisional-reference protocol is implemented
   and independently validated against intended Win16 semantics. Do not publish
   an initializing image as ready, deadlock on the current owner's transaction,
   or guess a guest error number. Other-owner loading/unloading is likewise not
   permission to expose an incomplete handle. Detect recursion before attempting
   a source lookup (ready-only liveModule currently cannot distinguish it).
   Nested FreeLibrary that would retire an actively executing module remains
   protected by call pins; termination reentry and stale handles need explicit
   tests before enabling that operation. Unsupported operations remain loud.

Scope decision

This checkpoint deliberately contains the evidence verifier and staged protocol,
not production changes. A correct general nested lifecycle requires request ABI,
driver propagation, explicit builtin lifetime and transaction tests together;
a WIN87EM-name special case would not implement that contract. Existing guards,
original bytes, module ownership and legacy loader remain unchanged. No build,
native guest, browser or original executable ran in this task.

Narrow fixed-builtin stage assessment (follow-up audit)

A synchronous fixed-builtin-only adapter could avoid the nested request ABI
entirely: decode the Win16 argument, acquire an already available dispatcher
identity and complete the far return in this same WAT invocation. Image-backed
and dynamic names must retain the current guard. This is a useful independent
first stage, but a name whitelist plus win16_h16 is not sufficient ownership.

The existing fixed imports are skipped in loadOwned and carry no dependency
reference. Existing legacy LoadLibrary increments refs only for dynamic IDs;
legacy FreeLibrary similarly ignores fixed IDs. GetModuleUsage scans loaded
images, so it returns zero for fileless builtins. Adding only an explicit-load
counter would omit WDIR62's own WIN87EM import reference. The bridge module
record's eight words are all occupied; its 24-bit dependency mask identifies
dynamic IDs 13..36. Adding the eleven fileless fixed IDs exceeds one DWORD.

Concrete smallest coherent stage: declare separate process-owned fixed counts
and per-importer fixed masks; acquire/link fixed import references while loading
each owned image, unwind them on rollback and final release, and count explicit
acquisitions separately enough to avoid consuming imports on invalid/double
FreeLibrary. Define handle creation/reuse and usage for that unified identity.
Process replacement clears the state under the existing arena lifetime rule.
Keep static dispatcher availability independent of guest refcounts, but never
claim a fabricated permanent guest reference. Share the lookup/accounting with
the narrow guarded Win16 load/free/usage adapters. Do not modify the singleton
PE request protocol or enable file-backed nested loading in this stage.

Primary reference inspected:
https://raw.githubusercontent.com/wine-mirror/wine/master/dlls/krnl386.exe16/ne_module.c
GetModuleUsage16 returns the resolved module count. NE_FreeModule decrements
that count and frees referenced modules after final termination; builtin modules
are actual lifetime objects there too. This supports real counted ownership,
not treating every builtin LoadLibrary as an uncounted successful handle.
Wine's image-backed builtin representation is not a blueprint for manufacturing
images in this emulator. Our fileless adapter still needs its own explicit state.

Counted fixed-builtin implementation checkpoint

The follow-up implements that narrow stage, pending build/native admission.
WIN16_PROCESS_ARENA grows from 8 to 208 declared bytes: offsets 0/4 remain
publication/pending-cleanup; 8..103 hold 24 fixed-import masks; 104..207 hold
13 pairs of import and explicit counters. The generated region mirror changes
the size/hash; subsequent bases do not move in the canonical layout. Full-arena
creation clears the extra state before publication. The formerly tempting
hidden-page 8f00 gap is occupied by QT stack leases and is not used.

Each lifecycle importer acquires its fixed edges in native code under its
unpublished record. Native rollback/final release removes those edges, after
WEP where applicable; failed WEP retains them. Explicit acquisitions increment
a separate process-owned count after successful alias allocation. Alias
exhaustion traps without holding the mutex or changing counts. Counts saturate
by rejecting a sum of 65535 rather than wrapping. Aliases remain while either
kind of reference lives and are forgotten on the final release. FreeLibrary
cannot consume import edges; invalid/double nested release remains diagnostic.

the complete Pascal stack/far return and bounded selector-relative string,
