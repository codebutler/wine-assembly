Contract blockers (unchanged, not solved by acquiring runtime access)
  The versioned DX6/7 COLORKEYBLENDENABLE state144 default and interaction with
  COLORKEYENABLE must be established from an original specification or native
  reference. The current state can round-trip but is not consumed in either
  renderer. A hardware document describing two available modes does not select
  the API's required mode. Do not assume universal any-contributing-tap reject.

  Ordinary filtered software keying still compares filtered RGB with a native
  key; even the all-key footprint has a determinate known failure. Mixed taps
  require a resolved contract for retaining RGB versus transparent-black
  replacement and rejection. Include zero-weight taps, all/none/mixed keys,
  duplicate RGB indices, addressing/border cases and truecolor fast16/general
  software routes when implementing that contract.

  DDPCAPS_ALPHA/key precedence is separately unresolved. GPU upload currently
  makes matching keys alpha0, while the fixed cutoff can also reject NONKEY
  palette entries below128. Real alpha is not key-membership metadata. Existing
  raw-key-over-alpha assertions characterize implementation, not normative
  behavior. Establish the precedence before blessing keyed alpha-palette
  outputs, then validate application alpha-test/blend/depth matrices on both
  renderer routes. Point-only identity repair does not complete filtered keys.
