### Source cause and narrow proposed repair (not implemented)

The page shadow itself is intentional: `host.js` creates GuestThreadHost with `_mainImports.host`, sets the page instance's `host_shadow`, and initializes its distinct host thread. `lib/guest-rpc.js` brokers to this shared host table. Registry lookup, shared-memory output writes and export resolution may legitimately use that shadow. **Executing guest GCO through storage's nested `ctx.exports.run` is not legitimate on it:** it has no owning guest stack/CPU context. The defect is that CoGetClassObject still requests host factory execution, unlike CoCreateInstance's existing resolve-only/owner-side continuation route. Do not copy the Worker's registers into the page or give the page a fabricated stack.

Proposed production scope for root review: **src/09a7-handlers-dispatch.wat**, **lib/storage.js**, and one focused COM owner/stack regression (tier registration only if required). CoGetClassObject should ask the host only to resolve the in-proc GCO export, then execute it on the current owning WAT instance. Preserve ordinary registered-class fast return and existing CoCreateInstance behavior. A private combined context-bit contract can distinguish resolve-only class-factory lookup from legacy host execution; the current `resolveOnly = !classFactoryOnly && bit40000000` explicitly prevents this combination and needs a precise compatibility test.

For a resolved GCO, an owner-side stdcall tail transfer may avoid allocating a new continuation: at CoGetClassObject entry E, original frame is return/CLSID/context/serverInfo/IID/out. GCO takes CLSID/IID/out. Read needed values before overwriting; write original return at E+8, CLSID at E+12, retain IID/out at E+16/+20, set ESP=E+8 and transfer to resolved GCO. Its ret12 then ends at E+24, the same final stack as CoGetClassObject's five-argument return. This must be tested with real x86 code and negative HRESULT/output cases before choosing it over a dedicated continuation. Preserve null-output/error contract and serverInfo/context limitations; do not broaden unsupported remote activation.

Regression should use **two real instances sharing memory**: page shadow deliberately ESP0, owning instance with valid nonzero stack; bridge resolution serviced on page, but a synthetic real guest GCO writes the requested factory, returns success or failure and observes requested CLSID/IID on owner. Assert zero page guest execution, unchanged shadow register/stack state, correct caller return/E+24, actual owner/thread, output, HRESULT, and a nested/yielding factory path if supported. Also cover unresolved DLL yield/retry, registered factory path, existing CoCreateInstance resolve contract and cooperative mode. No production source mutation/build or further runtime is authorized or performed yet.
