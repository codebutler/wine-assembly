## Actual execution path

* `tools/toyvm/arm-bench.js:92–107` already defines `jit-early`, `jit-r8`, `jit-sep`, **`jit-sepw`**, `jit-sepc`, **`jit-sepwc`**. The last two Worker arms mean separate-module preparation with/without continuous profiling. No new engine architecture is needed to test the user's idea.
* `run-dos.js:788–790` chooses `region-prepare.nodeWorkerBackend()` when `regionJit.worker` is true. At each guest slice, `:836–837` pumps and awaits **setImmediate**, not preparation completion, for Worker mode. Interpreter slices therefore continue while Worker work proceeds; the event-loop yield delivers its reply. Inline mode awaits the entire pending pipeline. Passing a Worker backend without setting the driver worker flag still causes the driver to wait.
* `region-live.js:94–124` implements the browser Worker using an importScripts bundle. `region-prepare.js:210–238` implements Node worker_threads. Both receive copied plain data. `region-live.js:264–304` synchronously copies guest memory, serializes arena/program metadata and snapshots registers/machine/handler-tail identity before posting. The snapshot is coherent at that guest seam, but copy/serialization are still foreground costs; no transfer list avoids the further structured-clone copy.
* Worker `prepareRegions` picks, lowers, audits and builds **Wasm bytes** (`region-prepare.js:143–145,182–194`). Gate execution may itself compile/instantiate temporary audit modules there. Returning final bytes is not the same as having a ready native compiled module installed in the running instance.
* **Separate path:** `region-live.js:464–467` calls `region-sep.installRegionModule`; `region-sep.js:96–106` uses synchronous `new WebAssembly.Module(bytes)` and `new WebAssembly.Instance(...)` on the interpreter thread, then grows/sets its table. Thus final validation/native compilation and instantiation still block the foreground, even in `jit-sepw`/`jit-sepwc`. Engine-internal caching may lower this cost; source cannot establish that it does.
* **Replacement path:** `region-live.js:471–478` awaits `makeVm`; `vm.js:73,102` awaits WebAssembly.compile/instantiate. It then copies current architectural state and rebinds the session/cache/machine. Main-thread Promise suspension is not guest suspension in a nonblocking driver; native compilation may run in browser engine workers while later guest slices continue. State carry itself is synchronous after completion.
* `region-live.js:353–386` only starts one pipeline (`busy`). Worker messages/Promise continuations execute on the same JS event loop between synchronous Wasm slices. There is no concurrent JS mutation inside a guest run, but long individual slices delay reply/install handling. Node's setImmediate avoids indefinite message starvation while a pipeline is pending; it does not impose a wall-time slice ceiling. Browser behavior depends on its normal scheduled frame loop, not just the presence of a Worker.

## Safety, bookkeeping and lifecycle findings

**Existing protection:** independent memory snapshot during preparation; handler-tail epoch check before install (`region-live.js:451–456`); exact guest-byte guards when a region head is decoded (`compile.js:437–444`); marked code ranges/invalidation and installed guard checks (`region-live.js:319–326,355–356`). Installation also repairs invalidated shadow return frames (`:626–676`). These mechanisms are material and should not be removed for speed.

**Concrete false bookkeeping:** `install()` can return false after an epoch mismatch, but `runPipeline()` ignores that result and increments installs/sets phase installed (`:428–431`). This can report a successful install when none happened. Fix narrowly: propagate successful/declined outcome and only count actual committed installs. Regression: grow handler tail during deferred preparation, assert no table mutation and no successful install count.

**Additional race to test, not demonstrated live:** replacement install checks extras epoch before awaiting makeVm, not again after that await. A foreground tree-fold pipeline can grow the handler tail while compilation awaits. Capture a session/VM generation and handler epoch; revalidate after asynchronous work and before commit. Also recheck prepared code assumptions then; current decode guards protect substitution, but stale preparation can still waste installation/invalidation work. Do not claim every changed byte necessarily runs stale code: existing guards matter.

**Stop/cancellation:** `region-live.js:693–698` stops the backend but has no stopped-generation flag to reject a late prepared result. Node `stop()` invokes terminate without awaiting completion; backend prepare has no exit/timeout settlement. Browser stop terminates but leaves its Promise unresolved. A queued result or asynchronous makeVm completion can outlive stop. Add per-run generation/request identity, bounded cancellation settlement, and commit-time live-generation check. Test stop during prepare/compile, worker error/exit and late reply; no stale install or leaked pending state.

**Node listener growth:** each preparation adds once(message) and once(error) handlers (`region-prepare.js:232–235`); successful messages do not remove the paired error listener. Continuous windows accumulate dormant error listeners. Remove both listeners when either path settles, also on exit/cancel. Browser handlers overwrite rather than accumulating, but lack request IDs and stop settlement.

**Continuous profile freshness:** seenHot uses arena head addresses (`region-live.js:361–366`) and is not a code-generation identity. Arena reuse can cause a new scene/code lifetime at an old address to be skipped; verify reuse/reset behavior before changing it. `sampling()` does not collect during busy preparation (`:230–234`), so preparation can miss a phase transition. Snapshot share is historical, not necessarily the future amortization share. Treat this as selection quality, distinct from code-byte correctness.

## Accounting and longer runs

`run-dos.js:504,947` uses whole-process process.cpuUsage, covering interpreter plus Node Workers and engine threads. Good primary total, but not latency or foreground pause attribution. Worker CPU reporting (`region-prepare.js:216–220`) exists only when process.threadCpuUsage exists. On a runtime without it, workerCpu is absent. `region-live.js:400–402` substitutes zero, so buildMs excludes Worker preparation CPU; browser Worker also never supplies workerCpu. **Do not call that buildMs total compilation CPU.** Individual stage fields are wall durations and should retain those units.

The subtraction `(elapsed - prepareWall + workerCpu)` mixes wall time and CPU. It can be a diagnostic estimate, not a clean additive CPU decomposition. WholeprocessCPU remains valid; expose preparation wall, worker threadCPU availability, foreground bundle/install wall and overlap progress separately. Don't manufacture zero for missing workerCPU.

`arm-bench.js:211` calibrates dispatch count from L1 **CPU seconds**, not requested wall seconds. `:221` retains best CPU result per arm rather than all repetitions; `:236,260` calls CPU-minus-build 'run'. Preserve every repeat and report paired distributions before drawing a precise benefit from longer runs. `run-dos.js:912` requests Worker stop without joining before final cpuUsage at947: incomplete/background compilation at end may be inconsistently charged. Record pending-at-stop, complete cancellation/join and distinguish pre-stop useful runtime from final cleanupCPU; do not extend guest execution just to finish compiling.

1. **Correctness/accounting first:** deferred backend unit tests for epoch-decline count, cancellation/late reply, listener cleanup and replacement-await epoch recheck. No broad JIT rewrite. BRW long-window frame mismatch remains an explicit blocker; +1 dispatch alone is tolerated, the wrong frame is not.
2. **Existing overlap A/B:** L1, jit-sep, jit-sepw, then continuous pair only after one-shot is clean. Same early6M+6M schedule and gate settings; 30/120/300 L1-CPU-second calibrated horizons, rotated repeated arms, one machine/no other jobs. Log guest dispatches at preparation start/result/install, installs/declines/stale reasons, per-stage wall/threadCPU, max foreground pause, region enters/share and pending-at-end. Falsifier: no guest progress during preparation, no useful installed region, or totalCPU/elapsed still worse after amortization. Longer runs can expose more wrong exits/SMC and are not merely a speed test.
3. **Remove final compile stall only if measured:** compile final bytes to WebAssembly.Module in preparation Worker and structured-clone the module, then instantiate against the live imports at the seam. Keep bytes for provenance/fallback; separate compile time from instantiate/table-commit time. Native-code reuse across cloning is engine-dependent; measure rather than promise it. Test same-process Worker/module transport on the actual Node/browser versions and exact imported mutable globals/table identity. This is the smallest relevant enhancement to sepWorker, not a new interpreter.
4. **Budget selection:** only after correctness and accounting, increase sample density/minimum sample count, skip low expected-benefit regions, and cool down repeated builds. Compare observed time remaining and entry counts against actual build/install cost. The continuous long-window prior result was worse, so more recompilation is not assumed beneficial.

## Amortization interpretation (root follow-up)

For matched useful work W in a stable phase, idealized totalCPU is `T_J(W)=B+J(W)` versus `T_L(W)=L(W)`. If approximately linear, `T_J=B+jW`, `T_L=lW`; break-even exists at `W>B/(l-j)` only when j<l. Longer matched runs can estimate slope/intercept, but profile delay, phase changes, repeated compilation and Worker contention violate that simple model. Record useful region coverage and each build; don't fit one straight line across different scenes blindly. Wall latency has overlapping preparation rather than a simply additive B, so estimate wall and wholeCPU separately.

The prior reported CPU-minus-build ratios do **not** prove the compiled steady body is slower: build accounting is mixed, interpreter executes before/around regions, coverage differs and longer arms may include more phases. They establish only that the reported aggregate has not paid back. First priority is the existing sep/sepw duration sweep with complete raw timing/coverage; compiled-Module transport is a small second experiment if measured foreground compile pauses matter. Phantom install is confirmed directly from false-return451–456 versus unconditional success428–431. Current box Node24.18.1 supports threadCpuUsage per root; old Node20 results must retain missing-workerCPU qualification, not inherit current capabilities retroactively.
