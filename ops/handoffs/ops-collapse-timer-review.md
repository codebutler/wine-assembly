## Three-function semantics

- `handle_timeSetEvent` retains the old inverted periodic bit as bit0 (1 means one-shot; 0 means periodic) and stores event mode bits0x10/0x20 alongside it. Ordinary callback flags leave mode0 and the same old0/1 values.
- `mm_timer_consume_slot` now tests bit0 rather than the entire word. This is necessary: otherwise an EVENT_SET periodic timer's0x10 would falsely retire it. Stored one-shot words0x11/0x21 retire after updating the due tick; stored periodic words0x10/0x20 survive. All three functions must move together.
- `mm_timer_due_slot` consumes a due event timer before host signaling, then continues scanning. It returns no event handle as a code pointer or MM_TIMER pseudo-message. PM_NOREMOVE may signal an event because signaling is independent of removing a message. EVENT_SET calls set_event; EVENT_PULSE calls set_event then reset_event. Ordinary mode0 still returns the due callback slot to the unchanged callback path.
- Existing `mm_timer_consume_due_tick` preserves periodic phase and coalesces lateness to one signal for the latest elapsed boundary; it does not promise one signal per missed tick. Cancellation retains the existing slot-ID mechanism. Event handle validity/errors and unsupported combined0x30 mode are not newly validated. Do not broaden this transplant to change those contracts.

The frozen base already imports set_event/reset_event and already calls due-slot processing from message polling and `fire_mm_timer`. Its parked-wait allowance is present. Event delivery can still be delayed by the unchanged active-callback/yield guards or an earlier due callback returned during scanning; this slice is not an independent timer thread or scheduling guarantee. Import/table/layout changes are unnecessary. Callback TLS/SEH context integration is outside this patch and must not be pulled in incidentally.

## SET wake/consumption path

Browser `host.js:1904–1911` forwards to ThreadManager. Frozen `setEvent` (`lib/thread-manager.js:1089`) atomically stores signaled, notifies, and queues existing waiter servicing. A SET timer intentionally leaves the event signaled until auto-reset acquisition or explicit reset. Repeated sets coalesce when already signaled; they are not counting-semaphore increments. `resetEvent:1198` clears state. Existing wait-all readiness checks defer consumption until all required objects are ready. These dependencies already exist in the selected base.

## PULSE limitation

The proposed PULSE is two calls, not an atomic operation that records the current waiter set. ThreadManager's `_wakeWaitersSoon` schedules a microtask; reset clears the shared state. Depending on cooperative versus Worker RPC scheduling, a waiter may be serviced between calls or may observe only the reset state. The cooperative host-import fallback likewise just toggles a Boolean. No pulse-specific waiter grant/latch is established by this patch. Consequently source inspection and a recorded set/reset pair do **not** prove delivery to an already waiting thread, manual/auto-reset waiter cardinality, or wait-all behavior. Retain this as a known limitation, not a task-expanding scheduler rewrite. If actual Collapse uses PULSE, qualify it only after a targeted real-wait discriminator or revise the source choice; do not silently assume SET evidence applies.
